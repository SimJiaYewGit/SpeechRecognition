# Architecture guide

The repository-root [architecture.pdf](../architecture.pdf) contains the component
diagram and an explanation of assumptions and validation limits. The editable
logical diagram is [architecture.mmd](architecture.mmd); the exact vector PDF
layout is generated by [build_architecture.py](build_architecture.py). Keep both
sources aligned when changing the architecture. PDF generation does not parse the
Mermaid source. Rebuild instructions and optional Python setup are in the README.

## Runtime flow

1. React selects local MP3s and sends one multipart request per file, sequentially.
   Vite proxies the same-origin API paths to the native backend on port 5000 or
   the Docker backend on port 8000, according to `BACKEND_URL`.
2. Flask validates the request, creates a sanitized unique filename using exclusive
   creation, and saves the recording. Original filenames remain in the database.
3. The transcriber acquires its nonblocking process-local lock, decodes MP3,
   downmixes to mono, resamples to 16 kHz, and checks decoded duration. Local
   Whisper Tiny generates text on CPU, with long-form generation above 30 seconds.
4. The repository commits filenames, text, and a UTC timestamp to SQLite before
   Flask returns 201. The UI refreshes its active list or filename search. A failed
   decode, inference, or database insert removes the saved file. An abrupt process
   crash can still leave an orphan because the database and filesystem do not
   share a transaction.
5. Listing and filename search use SQLite without invoking Whisper. Health checks
   model and database readiness. JSON responses travel through Flask and the
   development proxy to React. Health describes current readiness, not guaranteed
   future writes or free inference capacity.

## Model provisioning and persistence

Hugging Face is a model asset source, not a transcription service. Startup first
tries the cached snapshot, then downloads missing model assets if needed. Audio
and recognized text are processed locally; the application does not send them to
an external transcription API. Model loading failure leaves health at 503; restart
after fixing the cause to retry loading.

Compose uses separate named volumes for `/data` (SQLite and retained recordings)
and `/models` (model assets). Replacement containers reuse these volumes. Native
development defaults instead live under `backend/data` and `backend/.cache`.
Neither native storage nor the host virtual environment is copied into the image.

## Assumptions and considerations

- One Linux/x86-64 CPU backend replica with one Gunicorn worker and four threads.
  The process-local lock permits one decode/inference at a time; busy requests
  return 503. Scaling workers/replicas needs a shared capacity design and SQLite
  concurrency review. There is no background job queue.
- MP3 only, 25 MiB per complete request, and 600 seconds decoded duration by
  default. These limits are configurable. Long recordings require latency and
  memory measurements; the threaded worker timeout is not a hard request deadline.
- Local assignment deployment with no authentication, TLS, public hosting, or
  frontend image. Vite proxy configuration is only for development. Docker binds
  its published port to loopback and runs the process as UID/GID 10001.
- Automatic language detection and transcription rather than translation.
  Exact output is not guaranteed; human listening review is still pending.
- The supplied assignment begins at section 2. No missing section 1 requirements
  are inferred. No production throughput or exhaustive accessibility claim is made.
